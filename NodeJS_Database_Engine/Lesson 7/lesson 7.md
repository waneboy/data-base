# Лекция 7: Транзакции (ACID), откат изменений и сетевой TCP-сервер базы данных

> **Цель лекции:** Превратить нашу базу данных из локальной JS-библиотеки в полноценную клиент-серверную СУБД. Мы разберем реализацию транзакций и отката изменений (*Rollback*) через журнал Undo Log, разработаем собственный сетевой протокол (*Wire Protocol*) на сокетах Node.js и напишем клиентский драйвер (*SDK*).

---

## 1. Зачем базе данных сетевой сервер?

До сих пор наш код работал в одном процессе Node.js. Но реальные базы данных (PostgreSQL, MySQL, Redis) — это **сетевые демоны-серверы**.

Почему нельзя просто расшарить файл базы данных через общую сетевую папку (SMB/NFS) и дать клиентам писать в него напрямую?
1. **Безопасность и разграничение прав:** Клиент не должен иметь прямого доступа к файловой системе сервера.
2. **Конкурентные гонки:** Если 50 компьютеров одновременно попытаются сдвинуть указатель конца файла `table.db`, файл мгновенно повредится.
3. **Единая координация транзакций:** Только централизованный сервер может контролировать блокировки, журнал WAL и гарантировать целостность данных.

## 2. Анатомия транзакций: Как устроен `ROLLBACK`?

Слово **Транзакция** означает неделимую единицу работы. Классический пример — банковский перевод:
```sql
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 300 WHERE id = 1; -- Сняли у Алисы
UPDATE accounts SET balance = balance + 300 WHERE id = 2; -- Начислили Бобу
COMMIT;
```

Если сервер упадет или произойдет ошибка между первой и второй строчкой — деньги Алисы испарятся в никуда! СУБД обязана гарантировать свойство **Атомарности (Atomicity)**: либо выполняются *все* команды, либо *ни одной*.

### Как мы реализовали Undo Log (Журнал отката):

Каждое клиентское подключение получает собственный изолированный сессионный контекст:

```javascript
const session = {
  clientId: '127.0.0.1:54321',
  inTransaction: false,
  undoLog: [] // Стек компенсирующих действий
};
```

Когда клиент начинает транзакцию командой `BEGIN`, для каждой последующей мутации движок сохраняет в стек **обратное компенсирующее действие**:

| Прямая операция клиента | Что сохраняется в `undoLog` | Действие при `ROLLBACK` |
| :--- | :--- | :--- |
| `INSERT INTO users (id=5)...` | `{ type: 'UNDO_INSERT', id: 5 }` | Вызвать `storage.delete(5)` |
| `UPDATE users SET balance=700 WHERE id=1` | `{ type: 'UNDO_UPDATE', id: 1, previousState: { balance: 1000 } }` | Вызвать `storage.update(1, { balance: 1000 })` |
| `DELETE FROM users WHERE id=3` | `{ type: 'UNDO_DELETE', id: 3, previousState: { ... } }` | Вызвать `storage.insert(3, previousState)` |

Если клиент вызывает команду `ROLLBACK` (или сокет неожиданно обрывается из-за сбоя сети):
* Движок достает действия из `undoLog` **в обратном порядке (LIFO — Last In, First Out)**.
* Восстанавливает прежние значения полей и удаляет вставленные строки.
* База данных возвращается в идеальное состояние, которое было до начала транзакции!

## 3. Разработка сетевого протокола: `protocol.js`

TCP — это потоковый протокол (*Stream*), а не пакетный. Это означает, что если клиент отправил два сообщения по 100 байт, сервер в одном событии `'data'` может получить:
* 200 байт сразу (схлопывание пакетов);
* Либо сначала 50 байт, а потом 150 байт (фрагментация пакетов).

Если просто делать `JSON.parse(chunk)`, программа немедленно упадет с синтаксической ошибкой!

### Фреймирование с префиксом длины (Length-Prefixed Framing)
Мы разработали надежный протокол: перед каждым сообщением передается ровно **4 байта заголовка**, содержащих размер полезной нагрузки в формате `uint32` (Big-Endian):

```
┌───────────────────────────┬───────────────────────────────────────────┐
│ Заголовок: Длина (4 байта)│ Тело: Текстовый JSON в кодировке UTF-8    │
│   0x00 0x00 0x00 0x3A     │ {"query":"SELECT * FROM accounts;"}       │
└───────────────────────────┴───────────────────────────────────────────┘
```

В классе `Protocol` накопительный буфер `this.buffer` накапливает сырые байты сокета. Как только размер буфера превышает `4 + длина`, пакет вырезается и отправляется парсеру:

```javascript
while (this.buffer.length >= 4) {
  const msgLength = this.buffer.readUInt32BE(0);
  if (this.buffer.length >= 4 + msgLength) {
    const bodyBuf = this.buffer.subarray(4, 4 + msgLength);
    this.buffer = this.buffer.subarray(4 + msgLength);
    this.onMessage(JSON.parse(bodyBuf.toString('utf8')));
  } else {
    break; // Ждем следующую порцию данных
  }
}
```

## 4. Клиентский драйвер (Client SDK): `client.js`

Чтобы стороннее приложение на Node.js могло работать с нашей СУБД так же удобно, как с библиотеками `pg` или `mysql2`, мы создали класс `TinyClient`.

Он инкапсулирует TCP-сокет, автоматически кодирует запросы и возвращает промисы:

```javascript
import { TinyClient } from './client.js';

const client = new TinyClient({ host: '127.0.0.1', port: 8765 });
await client.connect();

const result = await client.query('SELECT * FROM accounts WHERE balance > 500;');
console.table(result.rows);

client.disconnect();
```

Скрипт `demo_client.js` поднимает сервер на порту `8899`, подключается клиентом и наглядно демонстрирует механизм банковского перевода с откатом.

node demo_client.js
