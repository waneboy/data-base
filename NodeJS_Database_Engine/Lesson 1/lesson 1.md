# Лекция 1: История баз данных: от перфокарт и файлового хаоса до NoSQL и NewSQL

> **Цель лекции:** Разобраться, почему появились базы данных, какую боль разработчиков 1960-х они решили, как математик из IBM навсегда изменил индустрию реляционной моделью и языком SQL, почему случился NoSQL-бум и как устроен ландшафт современных СУБД.

---

## 1. Доисторическая эпоха: как хранили данные без СУБД

Если спросить начинающего программиста: *«А зачем вообще нужна база данных? Ведь можно просто писать данные в файл `data.json` или `records.txt`?»*, он вряд ли сразу назовет фундаментальные причины. Но именно так человечество и начинало.

### Эра перфокарт и магнитных лент (1950–1960-е)

В 1950-х годах компьютерная память стоила астрономических денег, а вычислительные машины напоминали многотонные шкафы. Основными носителями информации были:

1. **Перфокарты** — картонные карточки с дырочками, пробиваемыми механически. Если оператор ронял стопку из 500 карт на пол — порядок данных терялся безвозвратно.
2. **Магнитные ленты (Magnetic Tapes)** — ленты с последовательным доступом. Чтобы найти запись под номером 10 000, магнитофон должен был физически перемотать несколько сотен метров пленки. Никакого случайного доступа (*Random Access*) не существовало: операционная сложность поиска составляла строгие $O(N)$.

```
[Лента: Запись 1] -> [Запись 2] -> ... -> [Запись 9999] -> [Запись 10000]
                                                            ^
                                           Приходилось мотать с самого начала!
```

С появлением первых жестких магнитных дисков (HDD) в 1956 году (знаменитый *IBM 305 RAMAC*, весивший тонну и вмещавший всего 5 мегабайт) появилась возможность адресовать произвольные сектора диска. Однако операционные системы тех лет не предлагали ничего, кроме работы с **«плоскими файлами» (Flat Files)**.

### В чем заключался кошмар файлового хранения?

Представьте, что вы пишете университетскую систему в 1965 году без СУБД. Каждый факультет заводит свой файл:
- Бухгалтерия создает файл `payroll.dat`.
- Деканат создает файл `students.dat`.
- Библиотека создает файл `library.dat`.

Каждый программист писал свои собственные процедуры на ассемблере, Фортране или Коболе для чтения бинарных структур с диска. Это породило четыре фундаментальные проблемы:

1. **Плотная связь логики приложения с физическим форматом данных (Data-Program Dependence):**
   Если деканат решал добавить студенту поле «номер телефона», размер бинарной структуры менялся. В ту же секунду **все программы**, которые читали этот файл, ломались с ошибками чтения смещения памяти. Чтобы добавить одну колонку, приходилось переписывать и перекомпилировать весь софт предприятия.
2. **Дублирование и рассинхронизация (Data Redundancy & Inconsistency):**
   Студент Иванов сменил фамилию. В деканате его обновили, а в библиотеке осталась старая фамилия, потому что файлы разные. Данные быстро превращались в кашу.
3. **Отсутствие параллельного доступа и гонки (Race Conditions):**
   Если два процесса одновременно открывали один и тот же файл на запись, данные последнего процесса затирали данные первого, либо файл повреждался на физическом уровне.
4. **Невозможность сложных запросов:**
   Чтобы ответить на простой вопрос: *«Назовите студентов 3 курса, у которых нет задолженностей в библиотеке и средний балл выше 4.5»*, нужно было вручную написать три программы с тройными вложенными циклами и временными файлами сортировки на диске.

Индустрия осознала: **данные должны быть отделены от кода**, а управление ими должно взять на себя специальное системное программное обеспечение.

## 2. Первое поколение: Иерархическая и Сетевая модели

В середине 1960-х годов стартовала знаменитая космическая программа «Аполлон» по высадке человека на Луну. Компания IBM получила заказ от NASA на создание системы контроля спецификаций ракеты-носителя «Сатурн-5», состоявшей из миллионов деталей. Так родилась первая промышленная СУБД.

### Иерархическая модель: IBM IMS (1968)

В 1968 году IBM представила **IMS** (*Information Management System*). Данные в ней организовывались в виде **дерева (графа без циклов)**, где у каждого узла-потомка мог быть строго один узел-родитель.

```
                  [ Завод (Factory) ]
                    /            \
        [ Цех 1 (Dept) ]        [ Цех 2 (Dept) ]
          /          \             /          \
   [ Деталь A ]  [ Деталь B ] [ Деталь C ] [ Деталь D ]
```

* **Плюсы:** Невероятная скорость при обходе дерева сверху вниз и естественное отражение древовидных иерархий (например, деталь состоит из подузлов).
* **Катастрофический минус:** Реальный мир не укладывается в чистое дерево. Как смоделировать отношение «многие-ко-многим»? Например, один студент учится у нескольких преподавателей, а один преподаватель учит сотни студентов. В иерархической модели приходилось либо дублировать ветки, либо заводить сложные костыли.

### Сетевая модель: CODASYL и Чарльз Бахман (1969)

Чтобы решить проблему иерархий, консорциум **CODASYL** под руководством легендарного Чарльза Бахмана (*Charles Bachman*, создателя IDS) разработал **сетевую модель данных**.

В сетевой модели потомок мог иметь несколько предков — данные представляли собой произвольный ориентированный граф.

```
       [ Студент 1 ]        [ Студент 2 ]
          \      /             /      \
        [ Курс: Базы данных ]   [ Курс: Архитектура ЭВМ ]
          /               \    /
     [ Преподаватель Иванов ]  [ Преподаватель Петров ]
```

Казалось бы, идеальное решение? Нет. В сетевой модели связи между записями реализовывались через **физические указатели (дисковые адреса блоков памяти)**.

Чтобы найти нужные данные, программист должен был написать процедурный код, буквально путешествующий по ссылкам:
```
MOVE FIRST Student WITHIN Class.
FIND NEXT Record USING Pointer.
IF NOT FOUND GOTO Error.
```

Программиста называли **«навигатором данных»** (*Data Navigator*). Если указатель ломался или структура менялась, база превращалась в запутанный клубок спагетти, из которого невозможно было извлечь связные сущности без повреждения связей.

Индустрия снова зашла в тупик. Требовался принципиальный математический прорыв.

## 3. Революция Эдгара Кодда и рождение реляционной модели (1970)

В 1970 году английский математик и ученый из IBM **Эдгар Франк Кодд (Edgar F. Codd)** опубликовал статью, перевернувшую мир компьютерных наук:

> **«A Relational Model of Data for Large Shared Data Banks»**  
> *(Реляционная модель данных для больших разделяемых банков данных)*

Кодд подошел к базам данных не как инженер по магнитным лентам, а как строгий математик. Он применил теорию множеств и логику предикатов первого порядка к хранению информации.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        Главная идея Кодда:                            │
│                                                                        │
│ Забудьте про физические диски, блоки, указатели и смещения памяти!    │
│ Пользователь и приложение должны видеть данные ИСКЛЮЧИТЕЛЬНО         │
│ в виде математических отношений (таблиц).                             │
│ Никаких указателей. Никаких ручных путей обхода.                       │
└────────────────────────────────────────────────────────────────────────┘
```

### Основные понятия реляционной модели

Кодд ввел строгую терминологию, которую разработчики позже перевели на язык практиков:

| Математический термин Кодда | Общепринятый термин в SQL | Суть понятия |
| :--- | :--- | :--- |
| **Отношение (Relation)** | **Таблица (Table)** | Двумерная структура из строк и столбцов |
| **Кортеж (Tuple)** | **Строка / Запись (Row)** | Единичный экземпляр сущности |
| **Атрибут (Attribute)** | **Столбец / Поле (Column)** | Свойство сущности определенного типа |
| **Домен (Domain)** | **Тип данных и ограничения** | Множество допустимых значений (например, `INT > 0`) |
| **Первичный ключ (Primary Key)** | **Первичный ключ** | Атрибут, гарантирующий уникальность строки |

Связи между таблицами перестали быть аппаратными дисковыми указателями! Теперь таблицы связывались исключительно по **значениям данных** через концепцию **внешнего ключа (Foreign Key)**.

### Реляционная алгебра

Кодд доказал, что над любыми таблицами можно выполнять математические операции, результатом которых всегда будет новая таблица:
1. **Селекция ($\sigma$):** Выборка строк по условию (будущий `WHERE`).
2. **Проекция ($\pi$):** Выборка определенных столбцов (будущий `SELECT id, name`).
3. **Декартово произведение ($\times$):** Комбинация всех строк одной таблицы со всеми строками другой.
4. **Объединение ($\cup$):** Склеивание двух совместимых таблиц (будущий `UNION`).
5. **Соединение ($\bowtie$):** Объединение записей по совпадению ключей (будущий `JOIN`).

### 12 правил Кодда (В переводе на понятный язык)

В 1985 году, когда маркетологи стали называть «реляционными» любые СУБД подряд, Кодд сформулировал 12 правил (на самом деле 13 — от правила 0 до 12). Ключевые из них:
* **Правило 0 (Фундаментальное):** СУБД должна управлять базами исключительно с помощью своих реляционных возможностей.
* **Правило 1 (Информационное):** Вся информация хранится только в таблицах на уровне логических значений.
* **Правило 2 (Гарантированный доступ):** К любому элементу данных можно обратиться по комбинации: *Имя таблицы + Первичный ключ + Имя колонки*.
* **Правило 3 (Обработка NULL):** СУБД должна систематически поддерживать понятие «значение неизвестно / отсутствует» (`NULL`), отличное от нуля или пустой строки.
* **Правило 8 и 9 (Физическая и логическая независимость данных):** Изменение формата хранения на диске (HDD на SSD, смена алгоритма индекса) или добавление новых колонок не должно требовать переписывания прикладного кода.

Руководство IBM поначалу проигнорировало работу Кодда: их СУБД IMS приносила миллионы долларов, и коммерциализировать новую разработку они не спешили. Но ученые в исследовательском центре в Сан-Хосе уже загорелись идеей.

## 4. Проект System R и рождение языка SQL

В 1974 году в лаборатории IBM в Сан-Хосе стартовал исследовательский проект **System R**. Его целью было доказать, что реляционную модель можно реализовать в железе с высокой производительностью.

В рамках System R инженеры **Дональд Чемберлин (Donald Chamberlin)** и **Рэй Бойс (Ray Boyce)** придумали язык запросов.

```
       Дональд Чемберлин и Рэй Бойс
                   │
                   ▼
          Сначала был SQUARE
   (математический, трудный для людей)
                   │
                   ▼
        Придумали SEQUEL (1974)
  Structured English QUEry Language
 (язык запросов, похожий на английский)
                   │
                   ▼
          Торговый спор с фирмой
          «Hawker Siddeley» (UK)
                   │
                   ▼
          Сократили до SQL (1979)
         Structured Query Language
```

### Декларативная парадигма: триумф абстракции

Главная прелесть SQL — его **декларативность**.

В императивных языках (C, Java, Python, JavaScript) вы описываете **КАК** делать задачу:
```javascript
// Императивный подход:
const results = [];
for (let i = 0; i < users.length; i++) {
    if (users[i].age > 18) {
        results.push({ name: users[i].name });
    }
}
```

В SQL вы описываете **ЧТО** вы хотите получить:
```sql
-- Декларативный подход:
SELECT name FROM users WHERE age > 18;
```

Как СУБД это сделает — использует ли B-Tree индекс, отсканирует ли весь диск, разделит ли задачу на 8 ядер процессора — решает внутренний модуль СУБД: **Оптимизатор запросов (Query Optimizer)**. Разработчик освобождается от рутины алгоритмизации ввода-вывода.

В рамках System R были придуманы практически все технологии, которые сегодня работают в PostgreSQL, MySQL и Oracle:
* Журнал опережающей записи **WAL (Write-Ahead Logging)** для отказоустойчивости.
* **Индексы B-Tree** для поиска за логарифмическое время.
* Иерархия блокировок и концепция транзакций **ACID**.
* Стоимостной оптимизатор запросов (*Cost-Based Optimizer* Патрисии Селинджер).

## 5. Эра коммерческих гигантов и открытого ПО

Пока IBM неспешно писала отчеты по System R, в 1977 году 33-летний калифорнийский программист **Ларри Эллисон (Larry Ellison)** вместе с двумя партнерами прочел технические публикации Чемберлина и Бойса.

Эллисон мгновенно понял колоссальный коммерческий потенциал реляционных баз данных. Они основали компанию *Software Development Laboratories* (позже переименованную в **Oracle**) и уже в 1979 году выпустили **Oracle V2** — **первую коммерческую реляционную СУБД на рынке**, опередив саму IBM! Первым крупным заказчиком Oracle стало ЦРУ США.

IBM спохватилась и выпустила **SQL/DS** (1981) и легендарную **DB2** (1983). В конце 1980-х компания Sybase представила свой SQL Server, архитектуру которого впоследствии лицензировала Microsoft, создав **Microsoft SQL Server**.

```
                        Хронология развития СУБД
1968 ── IBM IMS (Иерархическая)
1969 ── CODASYL DBTG (Сетевая)
1970 ── Эдгар Кодд: Реляционная модель
1974 ── System R и язык SEQUEL
1977 ── Ingres (Беркли, Стоунбрейкер)
1979 ── Oracle V2 (первая коммерческая SQL СУБД)
1983 ── IBM DB2
1989 ── Microsoft SQL Server 1.0 (совместно с Sybase)
1995 ── Появление MySQL 1.0
1996 ── PostgreSQL 6.0 (наследник Postgres)
2000 ── SQLite 1.0 (встраиваемая база)
2006 ── Google Bigtable (старт NoSQL)
2007 ── Amazon Dynamo
2009 ── MongoDB и Redis
2012 ── Google Spanner (NewSQL)
2020+ ─ Распределенный NewSQL и Векторные БД
```

### Университетская наука и революция Open Source

Параллельно с коммерческой веткой развивался свободный софт:

1. **Ingres и рождение PostgreSQL (Майкл Стоунбрейкер):**
   Профессор Калифорнийского университета в Беркли Майкл Стоунбрейкер создал альтернативный реляционный проект — **Ingres**. Позже он начал проект **Post-Ingres (Postgres)**, направленный на поддержку сложных типов данных и расширяемости. В 1996 году проект добавил полноценную поддержку SQL и получил имя **PostgreSQL**. Сегодня это самая технологически совершенная открытая РСУБД в мире.
2. **MySQL (Монти Видениус и Дэвид Аксмарк):**
   В 1995 году шведские разработчики создали легкую, фантастически быструю для простых веб-сайтов базу данных **MySQL** (названную в честь старшей дочери Монти — Мю). MySQL легла в основу стека LAMP (Linux, Apache, MySQL, PHP), на котором вырос весь современный интернет: от Википедии и WordPress до Facebook и YouTube.
3. **SQLite (Ричард Хипп):**
   В 2000 году Ричард Хипп разрабатывал софт для эсминцев ВМС США. Он устал от постоянных падений сетевых серверов БД и написал компактную библиотеку на C, которая хранила всю базу данных в одном обычном файле и не требовала никакого сервера и настройки. Сегодня **SQLite** установлена в каждом смартфоне (Android, iOS), в каждом браузере (Chrome, Firefox), операционных системах и автомобилях. Это самая используемая СУБД в истории человечества.

## 6. NoSQL бум 2000-х: почему реляционных баз стало мало?

На рубеже веков наступила эпоха Web 2.0. Количество пользователей сайтов измерялось уже не тысячами бухгалтеров компании, а сотнями миллионов людей со всего мира.

Реляционные базы столкнулись с непреодолимым барьером: **сложностью горизонтального масштабирования (Sharding)**.

Реляционная модель идеальна, когда база живет на одном мощном сервере. Но когда данных становится столько, что они не влезают на один диск, приходится делить таблицы между сотнями серверов. Выполнять `JOIN` между таблицами, расположенными на физически разных машинах через сеть — катастрофически медленно.

В 2006–2007 годах вышли две фундаментальные статьи интернет-гигантов:
* **Google Bigtable:** Распределенная колоночная система хранения для поиска и карт.
* **Amazon Dynamo:** Распределенное Key-Value хранилище высокой доступности для корзин покупателей интернет-магазина.

Так возникло движение **NoSQL** (*Not Only SQL* — «Не только SQL»).

### CAP-теорема Эрика Брюэра

В 2000 году профессор Эрик Брюэр сформулировал теорему, математически доказанную в 2002 году:

В любой распределенной системе хранения данных возможно обеспечить **не более двух из трех свойств одновременно**:

```
                       CAP ТЕОРЕМА
                          
                       Согласованность
                        (Consistency)
                            /   \
                           /     \
                          /       \
                         /  Р-СУБД \
                        / (в кластере)
                       /             \
                      /   MongoDB     \
                     /                 \
                    /                   \
                   /                     \
      Доступность ───────────────────────── Устойчивость к
     (Availability)      Cassandra          разделению сети
                          DynamoDB       (Partition Tolerance)
                          CouchDB
```

1. **C (Consistency — Согласованность):** Любое чтение с любого узла возвращает самую свежую запись либо ошибку.
2. **A (Availability — Доступность):** Каждый не упавший узел отвечает на запросы без ошибок, но не гарантирует самую свежую версию.
3. **P (Partition Tolerance — Устойчивость к разделению сети):** Система продолжает работать, даже если сетевой кабель между дата-центрами перерубили экскаватором.

> В реальном распределенном мире физические сбои сети неизбежны. Поэтому свойство **P обязательно**. Разработчикам приходится выбирать между **CP** (жертвуем доступностью ради непротиворечивости) и **AP** (жертвуем строгой согласованностью ради бесперебойной доступности).

### ACID против BASE

Классические РСУБД исповедуют философию **ACID**:
* **Atomicity** (Атомарность)
* **Consistency** (Согласованность)
* **Isolation** (Изолированность)
* **Durability** (Долговечность)

NoSQL-системы предложили альтернативу — модель **BASE**:
* **Basically Available** (Базовая доступность: система отвечает всегда, даже с деградацией сервиса).
* **Soft state** (Мягкое состояние: данные могут меняться со временем без входящих запросов).
* **Eventual consistency** (Согласованность в конечном счете: через несколько миллисекунд или секунд данные на всех репликах синхронизируются).

### 4 семейства NoSQL баз данных

1. **Ключ — Значение (Key-Value):** *Redis, Memcached.* Экстремально быстрые хранилища в оперативной памяти. Доступ по ключу за $O(1)$. Идеально для кэшей, сессий пользователей и счетчиков.
2. **Документные (Document-oriented):** *MongoDB, CouchDB.* Данные хранятся в виде иерархических документов (JSON/BSON). Нет строгой схемы: в одной коллекции у одного документа может быть 3 поля, у другого — 20. Идеально для быстрого стартаповского прототипирования и каталогов со сложной структурой.
3. **Колоночные (Wide-Column):** *Apache Cassandra, ScyllaDB, HBase.* Данные группируются по семействам колонок. Масштабируются на тысячи серверов, поддерживают сверхбыструю запись терабайтов логов и временных рядов (Time-Series).
4. **Графовые (Graph):** *Neo4j, Amazon Neptune.* Сущности представлены вершинами графа, а связи — ребрами со свойствами. Идеально для социальных сетей (поиск «друзей друзей»), систем рекомендаций и антифрод-мониторинга.

## 7. Современность: NewSQL, гибриды и векторные БД

К середине 2010-х индустрия пережила похмелье от NoSQL. Выяснилось, что жить без транзакций, с рассинхронизированными данными в финансах и интернет-магазинах — это катастрофа для бизнеса. Разработчики захотели вернуть строгость SQL и ACID, но сохранить горизонтальную масштабируемость NoSQL.

Так зародилось движение **NewSQL**:
* **Google Spanner:** Первая глобально распределенная база данных, использующая спутниковую связь GPS и атомные часы (*TrueTime API*) для точнейшей синхронизации транзакций между дата-центрами по всей планете.
* **CockroachDB и TiDB:** Свободные распределенные NewSQL-базы, использующие алгоритм консенсуса **Raft** и предоставляющие стандартный интерфейс PostgreSQL/MySQL с полной поддержкой ACID.

### Реляционные базы нанесли ответный удар

PostgreSQL и MySQL внедрили нативную поддержку типа данных `JSON/JSONB` с возможностью построения индексов по полям JSON-документов. Это стерло грань между Document-базами и классическими РСУБД: сегодня в 90% проектов PostgreSQL с легкостью заменяет MongoDB.

### 2023–2026: Взрыв векторных баз данных (Vector Databases)

С развитием больших языковых моделей (LLM) и генеративного искусственного интеллекта возник принципиально новый класс задач: хранение и поиск математических представлений текстов, картинок и звука — **векторных эмбеддингов** (массивов чисел из сотен измерений: `[0.124, -0.892, 0.441, ...]`).

Для поиска семантически похожих смыслов обычные B-Tree индексы бессильны. Появились специализированные векторные базы:
* **Qdrant, Pinecone, Milvus, Weaviate** — использующие алгоритмы приближенного поиска ближайших соседей (*HNSW — Hierarchical Navigable Small World*).
* Расширение **pgvector** для PostgreSQL, превращающее стандартный Postgres в полноценную векторную СУБД.
