# Лекция 4: Анатомия дискового хранилища: Форматы файлов, страницы и индексы

> **Цель лекции:** Понять физическую организацию данных на жестких дисках и SSD. Мы изучим модель Append-Only Log (Bitcask), классическую организацию дисковых страниц (Slotted Page), сравним строковое и колоночное хранение, а также разберем алгоритмы индексирования: Hash-таблицы, B+ Tree и LSM-деревья.

---

## 1. Физика носителей информации: Железный закон СУБД

Прежде чем написать хоть одну строчку кода хранилища, разработчик базы данных обязан понимать физику носителей, на которых эти байты живут.

### Жесткие магнитные диски (HDD)
HDD состоят из вращающихся алюминиевых или стеклянных пластин (со скоростью 5400–15000 об/мин) и механической головки чтения/записи на прецизионном приводе.
* Чтобы прочитать сектор в произвольном месте диска, головка должна физически переместиться к нужной дорожке и подождать, пока пластина повернется нужным сектором. Это время называется **Seek Time** (время позиционирования) и составляет **5–10 миллисекунд**.
* Это означает, что механический диск может выполнить всего **100–200 операций случайного чтения/записи в секунду (IOPS)**.
* Но если головка уже стоит на дорожке и пишет данные непрерывно друг за другом (**последовательная запись, Sequential I/O**), диск выдает скорость **150–250 мегабайт в секунду**!

### Твердотельные накопители (NVMe SSD)
В SSD нет механики: данные хранятся во флеш-памяти NAND.
* Время доступа составляет микросекунды, а случайные IOPS достигают сотен тысяч.
* Но у флеш-памяти есть архитектурная особенность: **чтение выполняется страницами (по 4–16 КБ), а стирание — только огромными блоками (по 2–8 МБ)**.
* Если СУБД делает бесконечные мелкие случайные перезаписи по 50 байт в середину файла, контроллер SSD вынужден постоянно считывать гигантский блок, стирать его и перезаписывать заново. Это явление называется **усилением записи (Write Amplification)**, что резко снижает ресурс диска и замедляет запись.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        ГЛАВНЫЙ ЗАКОН ДИСКОВЫХ СУБД:                    │
│                                                                        │
│   Последовательный ввод-вывод (Sequential I/O) ВСЕГДА драматически     │
│   быстрее случайного (Random I/O) — как на HDD, так и на NVMe SSD!     │
└────────────────────────────────────────────────────────────────────────┘
```

Именно вокруг этого закона построены все существующие форматы файлов баз данных.

## 2. Три ключевые модели организации файлов на диске

---

### Модель 1: Append-Only Log (Журнальное хранилище / Модель Bitcask)

Это самый простой, надежный и одновременно феноменально быстрый способ организации хранилища. Он лежит в основе архитектуры **Bitcask** (хранилище в Riak), Apache Kafka и журнала транзакций всех РСУБД.

#### Принцип работы:
* Файл базы данных открывается строго в режиме добавления в конец (**Append-Only**).
* Существующие байты на диске **никогда не изменяются и не перезаписываются**.
* Когда происходит `INSERT`, новая запись просто дописывается в конец файла.
* Когда происходит `UPDATE`, новая версия записи **снова дописывается в конец файла**!
* Когда происходит `DELETE`, в конец файла пишется специальная метка удаления — **Tombstone** («надгробный камень»).

```
[ Смещение: 0 ]    INSERT (id: 1, name: "Иван", age: 20)
[ Смещение: 54 ]   INSERT (id: 2, name: "Анна", age: 22)
[ Смещение: 108 ]  UPDATE (id: 1, name: "Иван", age: 21)   <-- Новая версия
[ Смещение: 162 ]  DELETE (id: 2) [Tombstone]              <-- Пометка удаления
```

#### В чем проблема?
Файл непрерывно растет, а на диске копится «мертвый груз» из устаревших версий записей.

#### Решение: Сжатие и уплотнение (Compaction / Merge)
Периодически база данных запускает фоновый процесс: она читает старый файл лога с начала до конца, оставляет для каждого ключа только самую последнюю актуальную версию, игнорирует удаленные записи и записывает компактный новый файл:

```
Старый лог (216 байт):  [id:1 v1] -> [id:2 v1] -> [id:1 v2] -> [id:2 DELETE]
                                  │ Фоновый Merge
                                  ▼
Новый лог (54 байта):   [id:1 v2]
```

### Модель 2: Постраничная организация (Page-based / Slotted Page)

Эта модель используется в классических реляционных СУБД: **PostgreSQL, Oracle, MySQL InnoDB, SQLite**.

Файл базы данных разбивается на фиксированные блоки одинакового размера — **страницы (Pages)**, обычно по 4096 или 8192 байта (в соответствии с размером кластера файловой системы ОС).

#### Архитектура страницы Slotted-Page:
Внутри страницы записи имеют разную длину (например, строка с именем может быть 5 символов, а может 200). Если просто складывать записи подряд, то при удалении или изменении строки в середине страницы образуется «дыра», и соседние записи придется сдвигать, пересчитывая все указатели в индексах!

Чтобы этого избежать, ученые придумали гениальную структуру **Slotted Page**:

```
┌────────────────────────────────────────────────────────────────────────┐
│ ЗАГОЛОВОК СТРАНИЦЫ (Page Header): ID страницы, свободное место         │
├────────────────────────────────────────────────────────────────────────┤
│ СЛОТ-МАССИВ (Line Pointers / Slots) ───► Растет СВЕРХУ ВНИЗ           │
│   [ Слот 0: смещение = 3900, длина = 196 ]                             │
│   [ Слот 1: смещение = 3650, длина = 250 ]                             │
│   [ Слот 2: смещение = 3400, длина = 250 ]                             │
│   ...                                                                  │
├────────────────────────────────────────────────────────────────────────┤
│                     СВОБОДНОЕ ПРОСТРАНСТВО (Free Space)                │
│                                                                        │
├────────────────────────────────────────────────────────────────────────┤
│ ТЕЛО ЗАПИСЕЙ (Tuples / Records) ◄────── Растет СНИЗУ ВВЕРХ            │
│   Запись 2: "Иван Смирнов..."                                          │
│   Запись 1: "Екатерина Попова..."                                      │
│   Запись 0: "Алексей Иванов..."                                        │
└────────────────────────────────────────────────────────────────────────┘
```

1. **Заголовок и массив слотов** растут от начала страницы вниз. Каждый слот — это крошечная запись (обычно 4 байта): *смещение данных от начала страницы* + *длина записи*.
2. **Сами записи данных** добавляются с конца страницы вверх навстречу массиву слотов.
3. **Почему это гениально:**
   Внешний идентификатор записи в базе (Tuple ID / RID) состоит из пары чисел: `(Номер страницы, Номер слота)`.
   Если запись внутри страницы изменила размер или была перемещена в процессе дефрагментации, **ее адрес `(Page 42, Slot 1)` не меняется**! Изменяется только внутреннее смещение в слоте. Ни один индекс в таблице перестраивать не нужно!

### Модель 3: Строковое (Row-Store) против Колоночного (Column-Store)

Как упаковывать данные на странице?

```
Данные: 
Строка 1: [ID: 1, Name: "Иван",  Age: 20, Balance: 1000]
Строка 2: [ID: 2, Name: "Анна",  Age: 25, Balance: 5000]
Строка 3: [ID: 3, Name: "Олег",  Age: 20, Balance: 300]
```

#### Строковое хранилище (Row-Store: OLTP)
Данные записываются строка за строкой подряд:
`[1, "Иван", 20, 1000], [2, "Анна", 25, 5000], [3, "Олег", 20, 300]`
* **Идеально для:** Онлайн-транзакций (OLTP) — интернет-магазинов, банков, веб-приложений. Когда нужно вставить одну строку или достать профиль одного пользователя (`SELECT * WHERE id = 1`), база считывает ровно один блок данных.
* **Катастрофа для аналитики:** Запрос `SELECT AVG(Balance) FROM users` вынужден прочитать с диска все имена, фамилии, пароли и адреса всех пользователей, чтобы просто достать одну колонку баланса!

#### Колоночное хранилище (Column-Store: OLAP)
Данные записываются по столбцам в отдельные блоки:
* Файл колонки ID: `[1, 2, 3]`
* Файл колонки Age: `[20, 25, 20]`
* Файл колонки Balance: `[1000, 5000, 300]`

* **Идеально для:** Аналитики больших данных (ClickHouse, Snowflake, Google BigQuery, Parquet).
* **Суперсила:** Однотипные данные в колонке сжимаются невероятно эффективно (алгоритмы RLE, Delta Encoding уменьшают объем на диске в 10–20 раз), а запрос `SELECT AVG(Balance)` считывает строго одну нужную колонку на скорости в десятки гигабайт в секунду.

## 3. Теория индексов: Как не сканировать миллионы записей

Если в таблице нет индекса, любой поиск превращается в **Full Table Scan (Полное сканирование)**. СУБД вынуждена прочитать с диска каждую страницу и каждую строчку таблицы. Сложность алгоритма — линейная $O(N)$. Если в таблице 100 000 000 строк, поиск займет минуты.

**Индекс** — это вспомогательная структура данных, которая хранит упорядоченные ключи и указатели на физическое положение записи на диске.

Разберем три фундаментальные структуры индексов.

---

### 1. Hash-индекс (Хеш-таблица)

Хранит в оперативной памяти хэш-таблицу: `Ключ -> Смещение на диске (offset)`.

```
Ключ (id)        Хэш-функция         Указатель в файле
  [ 42 ]   ──►  hash(42) = 0x3F  ──►  Файл: table.db, смещение: 12048 байт
```

* **Сложность:** Поиск точного совпадения `WHERE id = 42` происходит за мгновенные $O(1)$!
* **Фатальный недостаток:** Хеш-функция перемешивает порядок. По хэш-индексу **невозможно выполнять диапазонные запросы**:
  `WHERE id > 100` или `WHERE age BETWEEN 18 AND 25` или `ORDER BY created_at`.
  Для диапазонов придется сканировать всю таблицу целиком.

---

### 2. Сбалансированные B-деревья (B-Tree и B+ Tree)

Придуманы в 1970 году Рудольфом Байером и Эдвардом Маккрейтом. Это абсолютный король индексов в реляционном мире.

#### Почему не обычное бинарное дерево поиска (AVL или Красно-черное)?
В бинарном дереве у каждого узла максимум 2 потомка. Для миллиона записей глубина бинарного дерева составит около 20 уровней. Если каждый узел лежит в случайном месте на диске, поиск потребует **20 случайных обращений к диску**! Это 200 миллисекунд — целая вечность.

#### Идея B-Tree: высокий коэффициент ветвления (Fan-out)
Узел B-дерева делается размером ровно в дисковую страницу (например, 4 КБ). В такой блок помещается не 2, а **от 100 до 500 ключей и указателей**!

```
                            [ 20 | 50 ]                   <-- Корень
                           /     |    \
                          /      |     \
               [ 5 | 12 ]   [ 30 | 45 ]  [ 60 | 85 ]      <-- Листья
```

* Благодаря огромному ветвлению глубина B-дерева для 100 000 000 записей составляет всего **3–4 уровня**!
* При этом корень и верхние уровни постоянно висят в оперативной памяти. Найти любую запись среди миллиарда требует всего 1–2 реальных чтения с диска! Сложность: $O(\log N)$.

#### Отличие B+ Tree от обычного B-Tree:
В классическом B-Tree данные хранятся и в промежуточных узлах, и в листьях.
В **B+ Tree** (используется в InnoDB, Postgres, SQLite):
1. Промежуточные узлы хранят **только ключи-маршрутизаторы**.
2. **Все реальные данные и указатели на строки хранятся строго в листьях**.
3. **Все листья соединены между собой в двусвязный список**!

```
Лист 1 [ 1 | 5 | 9 ]  <──── Двусвязный ────►  Лист 2 [ 12 | 15 | 18 ]  <────►  Лист 3 [ 21 | ... ]
                             список
```

Благодаря связному списку листьев, диапазонный запрос `WHERE id >= 5 AND id <= 18` выполняется фантастически просто:
1. За $O(\log N)$ спускаемся по дереву к ключу `5` в Листе 1.
2. Дальше просто бежим по указателям вперед по листьям, пока ключ не превысит `18`. Никаких повторных подъемов по дереву!

---

### 3. LSM-Tree (Log-Structured Merge-tree)

Используется в высокопроизводительных системах записи: **RocksDB, LevelDB, Apache Cassandra, ScyllaDB, ClickHouse**.

В отличие от B-дерева, где обновление индекса требует перезаписи страниц в случайных местах диска (*Random Write*), в LSM-дереве случайная запись полностью ликвидирована!

```
                  Запись (INSERT / UPDATE)
                            │
                            ▼
     ┌──────────────────────────────────────────────┐
     │ 1. Журнал WAL на диске (Append-Only)         │ ──► Гарантия надежности
     └──────────────────────────────────────────────┘
                            │
                            ▼
     ┌──────────────────────────────────────────────┐
     │ 2. MemTable в оперативной памяти             │ ──► Вставка за O(log N)
     │    (Красно-черное дерево или SkipList)       │     без трогания диска
     └──────────────────────┬───────────────────────┘
                            │
                            │ При заполнении (Flush)
                            ▼
     ┌──────────────────────────────────────────────┐
     │ 3. SSTable на диске (Sorted String Table)    │
     │    [ Уровень L0: неизменяемые сортированные  │ ──► Последовательная запись
     │      файлы блоков данных ]                   │
     └──────────────────────┬───────────────────────┘
                            │ Фоновый процесс
                            ▼ Compaction (Слияние)
     ┌──────────────────────────────────────────────┐
     │ 4. Уровни L1, L2, L3...                      │
     └──────────────────────────────────────────────┘
```

1. Запись мгновенно попадает в память в **MemTable** (отсортированное дерево) и в журнал **WAL** на диске.
2. Когда память заполняется, MemTable сбрасывается на диск единым куском последовательной записи в виде файла **SSTable** (*Sorted String Table*).
3. Фоновый процесс **Compaction** берет несколько SSTable файлов и сливает их в один отсортированный файл (точно так же, как в классическом алгоритме сортировки слиянием *Merge Sort*).

## 4. Сравнительная таблица структур индексов

| Структура индекса | Поиск по точному ключу | Диапазонный поиск (`BETWEEN`) | Скорость вставки (`INSERT`) | Где применяется |
| :--- | :--- | :--- | :--- | :--- |
| **Hash Index** | $O(1)$ (Мгновенно) | Невозможно ($O(N)$) | $O(1)$ | Хэш-индексы Postgres, Redis |
| **B+ Tree** | $O(\log N)$ | $O(\log N + K)$ (Превосходно) | $O(\log N)$ (Случайный I/O) | PostgreSQL, MySQL, SQLite |
| **LSM-Tree** | $O(\log N)$ | $O(\log N + K)$ | $O(1)$ (Последовательный I/O) | RocksDB, Cassandra, ClickHouse |
