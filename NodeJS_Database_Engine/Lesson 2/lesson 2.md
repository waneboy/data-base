# Лекция 2: Под капотом СУБД: На каких языках их пишут и архитектурные слои

> **Цель лекции:** Заглянуть внутрь «черного ящика» любой базы данных. Мы разберем, почему создание СУБД — это вершина системного программирования, сравним C, C++, Rust, Go и Java в боевых движках и детально изучим 5 главных архитектурных слоев: от сетевого сокета до пластин жесткого диска.

---

## 1. Почему написание СУБД — это высший пилотаж?

Когда программист пишет обычный веб-сервис или мобильное приложение, он опирается на десятки слоев абстракций: фреймворки, виртуальные машины, среду исполнения и операционную систему.

Разработчик СУБД находится в принципиально иной ситуации: **он не может слепо доверять операционной системе (ОС)**.

### Дилемма кэширования: ОС против СУБД

Каждая операционная система (Linux, Windows, macOS) имеет собственный дисковый кэш страниц (*OS Page Cache*). Казалось бы: пусть ОС сама кэширует файлы базы данных в оперативной памяти? Но разработчики СУБД знают структуру своих данных на порядок лучше, чем ядро Linux:

1. **ОС ничего не знает о транзакциях:** Ядро ОС может решить сбросить измененную страницу памяти на диск в самый неподходящий момент — например, когда транзакция еще не закоммичена. Если в этот миг выключится питание, база данных превратится в испорченный мусор.
2. **Алгоритмы вытеснения страниц:** ОС обычно использует классический алгоритм LRU (*Least Recently Used*). Но если база данных выполняет последовательное чтение всей таблицы на 100 гигабайт (*Sequential Scan*), алгоритм LRU операционной системы вымоет из оперативной памяти все действительно важные индексы и горячие данные.

Поэтому серьезные базы данных открывают файлы с флагом `O_DIRECT` (в Linux), полностью отключая кэш операционной системы, и создают свой собственный менеджер памяти — **Buffer Pool**. СУБД фактически реализует внутри себя миниатюрную специализированную операционную систему!

## 2. На каких языках пишут современные СУБД?

Выбор языка программирования для ядра базы данных определяет ее предельную производительность, предсказуемость задержек (*latency*) и надежность. Разберем пять главных игроков индустрии.

```
                    Языковой ландшафт движков СУБД
                    
   [ C ] ──────────────► SQLite, PostgreSQL, Redis
   [ C++ ] ────────────► MySQL (InnoDB), ClickHouse, MongoDB, RocksDB
   [ Rust ] ───────────► SurrealDB, Meilisearch, Qdrant, TiKV
   [ Go ] ─────────────► CockroachDB, InfluxDB (ранние версии)
   [ Java ] ───────────► Apache Cassandra, Elasticsearch / Lucene, Neo4j
```

---

### 1. Язык Си (C): Абсолютный контроль и король времени

Си — нестареющая классика системной инженерии. На нем написаны **PostgreSQL**, **SQLite** и **Redis**.

#### Почему Си:
* **Нулевой оверхед (Zero Overhead):** Никакой скрытой магии, никакой тяжелой виртуальной машины, никаких фоновых сборщиков мусора. Каждая строчка кода транслируется в предсказуемый набор инструкций ассемблера.
* **Прямая работа с системными вызовами ядра:** Системные вызовы `mmap`, `fsync`, `io_uring`, `epoll` являются нативными для Си.
* **Фантастическая переносимость:** Код SQLite на ANSI C можно скомпилировать под тостер, космический аппарат, марсоход, смарт-часы и суперкомпьютер.

#### В чем боль:
* **Ручное управление памятью:** Разработчик лично вызывает `malloc` и `free`. Ошибка на один байт приводит к утечкам памяти, порче соседних страниц (*Buffer Overflow*) или мгновенному аварийному завершению процесса (*Segmentation Fault*).
* **Отсутствие современных абстракций:** Нет обобщенных типов (*Generics*), перегрузки операторов и удобных коллекций. Приходится изобретать собственные структуры данных на макросах и указателях на функции `void*`.

### 2. Язык C++: Мощь шаблонов и SIMD-векторизация

C++ стал стандартом де-факто для высокопроизводительных движков: ядро **InnoDB** в MySQL, колоночный монстр **ClickHouse**, движок хранения **RocksDB** от Meta, **MongoDB** и **ScyllaDB**.

#### Почему C++:
* **Концепция RAII (Resource Acquisition Is Initialization):** Ресурсы (дескрипторы файлов, захваченные мьютексы, участки памяти) автоматически освобождаются при выходе переменной из области видимости. Это спасает от 90% утечек памяти.
* **Шаблоны и инлайнинг без потери скорости (*Zero-cost abstractions*):** Вы можете писать красивый объектно-ориентированный код, который компилятор сожмет в монолитный ассемблерный блок, работающий со скоростью Си.
* **Векторизация и SIMD (Single Instruction, Multiple Data):**
  Например, отечественная СУБД **ClickHouse** обрабатывает сотни миллионов строк в секунду именно благодаря C++ и векторным инструкциям процессора (AVX-2, AVX-512). Вместо того чтобы складывать числа по одному в цикле, процессор за один такт складывает 16 чисел сразу!

```
Классический скалярный цикл (по одному числу):
[ 1 ] + [ 5 ] = [ 6 ]  (Такт 1)
[ 2 ] + [ 3 ] = [ 5 ]  (Такт 2)
[ 7 ] + [ 1 ] = [ 8 ]  (Такт 3)
[ 4 ] + [ 2 ] = [ 6 ]  (Такт 4)

SIMD-векторизация в ClickHouse (один процессорный такт):
[ 1 | 2 | 7 | 4 ]  +  [ 5 | 3 | 1 | 2 ]  =  [ 6 | 5 | 8 | 6 ]  (Такт 1!)
```

#### В чем боль:
* Чрезвычайная сложность стандарта, риск нарваться на неопределенное поведение (*Undefined Behavior*) и многочасовая компиляция больших проектов.

### 3. Rust: Новая эра безопасного системного программирования

Если бы сегодня создавали PostgreSQL с нуля, его почти наверняка написали бы на **Rust**. За последние годы на Rust созданы суперзвезды нового поколения СУБД: **SurrealDB**, векторная база **Qdrant**, поисковый движок **Meilisearch**, распределенный KV-движок **TiKV** и движок SQL-аналитики **Apache DataFusion**.

#### Почему Rust:
* **Безопасность памяти без сборщика мусора:** Уникальная модель владения (*Ownership & Borrowing*) гарантирует на этапе компиляции, что в программе не будет повисших указателей (*Dangling Pointers*), двойных освобождений памяти (*Double Free*) и состояний гонки (*Data Races*).
* **Предсказуемый ультранизкий latency:** В отличие от языков с GC, у Rust нет пауз: время отклика исчисляется микросекундами.
* **Современные абстракции:** Паттерн-матчинг, алгебраические типы данных, встроенный асинхронный рантайм (*Tokio*), отличная система пакетов `Cargo`.

---

### 4. Языки со сборщиком мусора: Java и Go

На **Java** написаны такие промышленные гиганты, как **Apache Cassandra**, распределенная поисковая система **Elasticsearch** (на базе движка Apache Lucene) и графовая СУБД **Neo4j**. На **Go** написаны NewSQL база **CockroachDB** и тайм-сериес СУБД **InfluxDB**.

#### Почему их выбирают:
* Колоссальная скорость разработки и удобство: программистам не нужно думать о выделении каждого байта памяти.
* Потрясающая стандартная библиотека для работы с сетью и многопоточностью (горутины в Go). Идеально для написания распределенных сетевых кластеров и реализации консенсуса (Raft, Paxos).

#### Главная проблема: Паузы сборщика мусора (GC Pauses)

В языках со сборщиком мусора (особенно JVM) периодически наступает фаза **Stop-The-World**: виртуальная машина приостанавливает выполнение всех рабочих потоков, чтобы найти неиспользуемые объекты и освободить оперативную память.

Представьте: банковская система обрабатывает транзакции. Вдруг JVM решает собрать мусор в куче размером 64 ГБ. Все запросы клиентов подвисают на 300–500 миллисекунд. Для финансовых торгов и высоконагруженных систем такие задержки недопустимы!

> **Показательный исторический факт:**
> Создатели базы данных *InfluxDB* изначально написали ее ядро на Go. Но из-за проблем с потреблением памяти и задержками сборщика мусора при хранении миллиардов временных точек они полностью переписали свое новое ядро хранения **IOx на язык Rust**!
> Аналогично создатели **ScyllaDB** полностью переписали **Cassandra с Java на C++**, получив десятикратное снижение задержек и аппаратных затрат.

## 3. Анатомия классической СУБД: 5 ключевых слоев

Любая серьезная система управления базами данных — будь то Oracle, Postgres или самодельная учебная база — устроена по модульному принципу и состоит из 5 базовых уровней:

```
┌────────────────────────────────────────────────────────────────────────┐
│ 1. ТРАНСПОРТНЫЙ УРОВЕНЬ (Connection Manager & Transport)               │
│    Сетевые сокеты TCP, TLS-шифрование, аутентификация, Connection Pool │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │  Сырая строка SQL
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 2. ПРОЦЕССОР ЗАПРОСОВ (Query Processor)                                │
│    [ Лексер ] ──► [ Парсер ] ──► [ AST Дерево ] ──► [ Оптимизатор ]     │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │  Оптимальный план выполнения (Plan)
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 3. ДВИЖОК ВЫПОЛНЕНИЯ (Execution Engine)                                │
│    Итераторы Volcano (Scan, Filter, HashJoin, Sort, Aggregate)         │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │  Запросы страниц и кортежей
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 4. ДВИЖОК ХРАНЕНИЯ (Storage Engine)                                    │
│    Buffer Pool (кэш в RAM) ◄──► Индексы (B+ Tree / Hash) ◄──► Pager    │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │  Чтение / запись блоков данных
                                   ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 5. ПОДСИСТЕМА НАДЕЖНОСТИ (WAL, Lock Manager, Recovery)                 │
│    Журнал Write-Ahead Log, блокировки таблиц/строк, MVCC-версии        │
└──────────────────────────────────┬─────────────────────────────────────┘
                                   │  fsync()
                                   ▼
                     Физический диск (HDD / NVMe SSD)
```

Разберем назначение каждого уровня.

### 1. Транспортный уровень (Connection & Transport)
Отвечает за сетевую коммуникацию. База данных слушает сетевой порт (например, `5432` у Postgres или `3306` у MySQL).
* Принимает входящие TCP-соединения клиентов.
* Проверяет пароли и права доступа (авторизация).
* Поддерживает архитектуру обработки соединений:
  - *Process-per-connection* (как в классическом PostgreSQL, где на каждого клиента форкается отдельный процесс ОС).
  - *Thread-per-connection* (как в MySQL).
  - *Асинхронный Event Loop / Epoll* (как в Redis и Node.js).

### 2. Процессор запросов (Query Processor)
Превращает человекочитаемую строку текста SQL в исполняемую машинную инструкцию:
1. **Лексер (Токенизатор):** Разбивает строку `SELECT * FROM users` на кирпичики: `KEYWORD(SELECT)`, `STAR`, `KEYWORD(FROM)`, `IDENTIFIER(users)`.
2. **Синтаксический анализатор (Parser):** Проверяет грамматику и строит **AST (Abstract Syntax Tree)** — древовидную модель запроса.
3. **Оптимизатор запросов (Query Optimizer):** Сердце процессора. Один и тот же SQL-запрос можно выполнить десятками разных способов. Например, таблицу `A` можно соединить с `B` через вложенные циклы (*Nested Loops*), сортировку слиянием (*Merge Join*) или хэширование (*Hash Join*). Оптимизатор считает математическую стоимость каждого варианта по статистике и выбирает самый быстрый план!

### 3. Движок выполнения (Execution Engine)
Берет план выполнения и запускает обход данных. В большинстве СУБД используется классическая **модель итераторов Волкано (Volcano Iterator Model)**, предложенная ученым Гоецем Граефе (*Goetz Graefe*).

Каждый оператор плана (Scan, Filter, Join) представляет собой итератор с тремя методами:
* `open()` — инициализация оператора.
* `next()` — отдать следующую запись (кортеж).
* `close()` — завершить работу и освободить память.

```
                  [ Output To Client ]
                           ^
                           │ next()
                  [ Filter (age > 18) ]
                           ^
                           │ next()
                  [ Index Scan (users) ]
```
Записи передаются конвейером снизу вверх по одной штуке, благодаря чему не нужно загружать всю многомиллионную таблицу целиком в память!

### 4. Движок хранения (Storage Engine)
Слой, который отвечает за организацию данных в байты:
* **Pager:** Читает и записывает данные с физического диска фиксированными порциями — страницами (*Pages*) размером обычно по 4, 8 или 16 килобайт.
* **Buffer Pool:** Держит в оперативной памяти массив страниц и управляет их обновлением.
* **Индексы (B+ Tree, Hash):** Специальные структуры для мгновенного нахождения нужной страницы на диске по значению ключа.

### 5. Подсистема надежности и транзакций (Recovery & Transactions)
Гарантирует, что данные не исчезнут, даже если сервер физически выдернут из розетки:
* **Write-Ahead Logging (WAL):** Прежде чем страница с данными на диске будет изменена, факт изменения сначала записывается в последовательный журнал предзаписи и сбрасывается на диск через `fsync()`.
* **Lock Manager & MVCC:** Обеспечивает изолированность параллельных транзакций, предотвращая конфликты одновременного чтения и записи.

## 4. Сравнительная матрица языков системного программирования для СУБД

| Критерий | C (Си) | C++ | Rust | Go | Java |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Управление памятью** | Ручное (`malloc`/`free`) | Ручное + RAII | Система владения (Compile-time) | Сборщик мусора (GC) | Сборщик мусора (GC) |
| **Паузы выполнения** | Отсутствуют (0 мс) | Отсутствуют (0 мс) | Отсутствуют (0 мс) | Есть (паузы GC) | Есть (тяжелый GC) |
| **Безопасность параллелизма** | На совести автора | На совести автора | Гарантирована компилятором | Гонки возможны в рантайме | Гонки возможны в рантайме |
| **Скорость выполнения** | Максимальная | Экстремальная (SIMD) | Максимальная | Средняя/Высокая | Средняя/Высокая |
| **Скорость разработки** | Медленная | Средняя | Средняя | Очень быстрая | Быстрая |
| **Примеры в проде** | PostgreSQL, SQLite | MySQL, ClickHouse | Qdrant, SurrealDB | CockroachDB | Cassandra, Elastic |
