# Лекция 5: Практика: Пишем свой движок хранения (Storage Engine) на Node.js с нуля

> **Цель лекции:** Перестать быть просто потребителем чужих баз данных и написать собственное ядро хранения на Node.js. Мы реализуем промышленную модель **Bitcask**: бинарный формат записей с проверкой контрольных сумм CRC32, in-memory хэш-индекс для выборки за $O(1)$, журнал предзаписи WAL и процедуру сжатия данных (*Compaction*).

---

## 1. Архитектурная концепция: Почему именно модель Bitcask?

Когда инженеры компании Basho разрабатывали распределенную СУБД Riak, перед ними встала задача: создать локальный движок хранения ключей и значений (*Key-Value Storage Engine*), который обладал бы предельной скоростью записи, предсказуемым временем чтения и абсолютной надежностью при внезапных сбоях питания.

Так появилась модель **Bitcask**. Ее архитектура элегантна и проста:

1. **Файл на диске — это Append-Only Log:** Все операции (`INSERT`, `UPDATE`, `DELETE`) дописываются исключительно в конец файла. Мы никогда не перезаписываем существующие секторы диска. Это дает максимальную скорость последовательного ввода-вывода (*Sequential I/O*).
2. **Индекс в оперативной памяти (Keydir):** В памяти процесса живет простая хэш-таблица (`Map` в JavaScript), где каждому идентификатору строки (`id`) сопоставлена структура с координатами: `{ offset, length }`.
3. **Чтение за $O(1)$:** Чтобы прочитать строку, мы мгновенно берем ее смещение из памяти и делаем **ровно одно позиционное чтение** с диска!

```
                  ОПЕРАТИВНАЯ ПАМЯТЬ (RAM)
                  Keydir (Хэш-индекс)
                  ┌───────┬─────────┬────────┐
                  │  ID   │ Offset  │ Length │
                  ├───────┼─────────┼────────┤
                  │   1   │   158   │   78   │ ──────────────┐
                  │   2   │    0    │   80   │ ───────┐      │
                  └───────┴─────────┴────────┘        │      │
                                                      │      │
                  ФИЗИЧЕСКИЙ ДИСК (table.db)          ▼      ▼
                  [ Запись ID=2 (80B) ] ... [ Запись ID=1 (78B) ]
```

## 2. Разработка бинарного формата записи

Чтобы защитить базу от повреждений и эффективно читать данные, каждая запись на диске предваряется **фиксированным бинарным заголовком размером ровно 16 байт**.

### Структура заголовка (Header — 16 байт)

```
0       2       4               8              12             16 (Байты)
┌───────┬───────┬───────────────┬──────────────┬──────────────┐
│ MAGIC │ TYPE  │   RECORD ID   │  DATA LENGTH │    CRC-32    │
│ 0xD801│ 1 или 2│ (uint32, 4B)  │ (uint32, 4B) │ (uint32, 4B) │
└───────┴───────┴───────────────┴──────────────┴──────────────┘
```

1. **Magic Number (2 байта, `0xD801`):** Специальная числовая сигнатура («магическое число»). Если при чтении файла первые 2 байта не равны `0xD801`, движок понимает: файл поврежден или это не наш формат.
2. **Type (2 байта):** Тип записи:
   * `1` — обычная запись с данными (`RECORD`).
   * `2` — метка удаления (`TOMBSTONE`).
3. **Record ID (4 байта, `uint32`):** Числовой идентификатор записи (первичный ключ, от 0 до 4 294 967 295).
4. **Data Length (4 байта, `uint32`):** Размер тела данных (Payload) в байтах.
5. **CRC32 Checksum (4 байта, `uint32`):** Контрольная сумма алгоритма IEEE 802.3, вычисленная от тела данных. Если во время записи выключился свет, контрольная сумма не совпадет, и поврежденная запись будет безопасно отброшена при старте.

## 3. Реализация журнала предзаписи: `wal.js`

Журнал опережающей записи **WAL (Write-Ahead Log)** реализует букву **D (Durability)** стандарта ACID. 

Прежде чем вносить запись в основной файл или обновлять индекс в памяти, операция записывается в текстово-бинарный журнал `table.wal` и принудительно сбрасывается на физический диск с помощью системного вызова `fsync()` (в Node.js: `fileHandle.sync()`).

### Код алгоритма CRC32 и класса WAL:

```javascript
// Предвычисленная таблица для канонического алгоритма CRC32 (IEEE 802.3)
const CRC32_TABLE = new Uint32Array(256);
for (let i = 0; i < 256; i++) {
  let c = i;
  for (let k = 0; k < 8; k++) {
    c = (c & 1) ? (0xEDB88320 ^ (c >>> 1)) : (c >>> 1);
  }
  CRC32_TABLE[i] = c >>> 0;
}

export function calcCRC32(input) {
  const buf = typeof input === 'string' ? Buffer.from(input, 'utf8') : input;
  let crc = 0xFFFFFFFF;
  for (let i = 0; i < buf.length; i++) {
    crc = CRC32_TABLE[(crc ^ buf[i]) & 0xFF] ^ (crc >>> 8);
  }
  return (crc ^ 0xFFFFFFFF) >>> 0;
}
```

Метод `wal.log(op, id, data)` формирует строку с префиксом CRC32, пишет ее в файл и гарантирует физический сброс буфера ОС на накопитель:

```javascript
async log(op, id, data = null) {
  const payload = JSON.stringify({ timestamp: Date.now(), op, id, data });
  const crc = calcCRC32(payload).toString(16);
  const entry = `${crc}:${payload}\n`;

  await this.fileHandle.write(entry);
  await this.fileHandle.sync(); // Гарантированный сброс на диск!
}
```

## 4. Реализация движка хранения: `storage_engine.js`

Разберем ключевые методы нашего класса `StorageEngine`.

### 1. Инициализация и построение индекса (`buildIndexFromDisk`)

При старте базы данных мы открываем файл `table.db` и последовательно читаем заголовки всех записей от нулевого смещения до конца файла:

```javascript
while (offset + HEADER_SIZE <= this.currentFileSize) {
  await this.fileHandle.read(headerBuf, 0, HEADER_SIZE, offset);
  
  const magic = headerBuf.readUInt16BE(0);
  const type = headerBuf.readUInt16BE(2);
  const id = headerBuf.readUInt32BE(4);
  const dataLen = headerBuf.readUInt32BE(8);
  const totalRecordSize = HEADER_SIZE + dataLen;

  if (type === TYPE_RECORD) {
    // Актуальное смещение последней версии записи
    this.keydir.set(id, { offset, length: totalRecordSize });
  } else if (type === TYPE_TOMBSTONE) {
    // Запись была удалена позже — удаляем из индекса
    this.keydir.delete(id);
  }
  
  offset += totalRecordSize;
}
```

### 2. Вставка и обновление (`insert` и `update`)

Вставка и обновление в модели Append-Only работают по единому принципу — данные пишутся в конец файла:

```javascript
async insert(id, data) {
  if (this.keydir.has(id)) {
    throw new Error(`Duplicate entry: ID=${id} уже существует.`);
  }

  // 1. Пишем в журнал WAL
  await this.wal.log('INSERT', id, data);

  // 2. Кодируем в бинарный буфер (16 байт заголовок + JSON полезной нагрузки)
  const recordBuf = this.encodeRecord(TYPE_RECORD, id, data);
  const offset = this.currentFileSize;

  // 3. Пишем в конец файла и сбрасываем кэш
  await this.fileHandle.write(recordBuf, 0, recordBuf.length, offset);
  await this.fileHandle.sync();

  // 4. Обновляем хэш-индекс в памяти
  this.keydir.set(id, { offset, length: recordBuf.length });
  this.currentFileSize += recordBuf.length;

  return { id, ...data };
}
```

### 3. Точечное чтение по первичному ключу за $O(1)$ (`get`)

Чтение выполняется молниеносно: мы не перебираем записи в файле, а сразу обращаемся к байтовому смещению:

```javascript
async get(id) {
  const entry = this.keydir.get(id);
  if (!entry) return null;

  // Читаем ровно длину записи по точным координатам
  return await this.decodeRecordAt(entry.offset);
}
```

### 4. Процедура сжатия (Компактификация / Compaction)

Поскольку файл базы данных только растет, старые перезаписанные строки и удаленные объекты (надгробия) занимают место. Метод `compact()` решает эту проблему:
1. Создает временный файл `table.db.compact`.
2. Обходит только активные ключи из оперативной памяти `keydir`.
3. Записывает их непрерывно друг за другом с новыми смещениями.
4. Атомарно переименовывает файл через `fs.rename()`, подменяя старый раздутый файл на свежий и компактный!
